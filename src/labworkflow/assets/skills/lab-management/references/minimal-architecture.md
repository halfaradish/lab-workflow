# 最小实现与复杂度预算

这份参考只回答一个问题：**为了验证一个想法，最少需要写多少代码？**

实验的目的不是交付一个可维护系统，而是尽快得到一个可信的结论。实验代码通常会被
丢弃、归档或只把其中一小段 promote 出去。因此默认策略是：

> 用最短能证伪假设的实现；只有假设本身要求时，才引入复杂度。

## 复杂度预算

一次实验默认只允许：

- **1 个问题**：一句可证伪的假设；
- **1 个入口**：一个脚本、一个页面或一个命令；
- **0–1 个新依赖**：优先标准库；新增依赖必须服务于成功标准；
- **0 个新服务**：不启动数据库、队列、缓存、Web 服务，除非假设就是验证它们；
- **0 层抽象**：不为了复用拆包、不写通用框架、不做依赖注入；
- **1 个时间盒**：60–120 分钟；到点记录，不扩大范围。

如果实验需要更多，先证明简单方案为什么不够。

## 三问

每次准备加东西时问：

1. **它帮助验证哪条成功标准？** 答不出来就不加。
2. **去掉它，实验还能不能得出结论？** 能就不加。
3. **假设被证伪后，这段代码会被丢掉吗？** 会——那就写得越简单越好。

## 红牌清单

出现以下信号时，停下来检查是否过度设计：

- 为几十行脚本建 `src/`、`domain/`、`services/`、`adapters/` 多层目录；
- 为一次性数据引入数据库、ORM、迁移、连接池；
- 为本地脚本加 HTTP API、认证、权限、多租户；
- 为两个实现加插件系统、事件总线、依赖注入容器；
- 为了「以后可能复用」写配置层、适配器层、通用接口；
- 为实验加 Docker Compose、K8s、CI/CD、监控栈；
- 为一次性代码追求 100% 覆盖率和完整测试金字塔；
- 在实验还没跑通前就开始重构、抽包、写文档站；
- 把模板自带的 `main.py` / `src/index.js` 改造成框架骨架。

这些做法在正式项目中可能有意义，但会把「验证一个假设」变成「建设一个系统」。

## 按实验类型选择最小形态

### API / 库能力验证

```text
一个脚本 + 一个函数 + 一次真实调用
```

只验证「能不能用、行为是否符合预期」。不要先搭客户端封装、重试、配置系统。

### 两种方案对比

```text
一个脚本 + 两个函数/两组参数 + 同一份输入 + 同一个计时器
```

共用输入和测量逻辑，避免为了公平性给每个方案搭一套框架。

### 性能 / 基准

```text
最小复现 + 固定数据 + 固定环境 + 多轮计时
```

先跑通再谈统计显著性；不要先搭压测平台。

### 数据处理

```text
一个小样本 + 本地文件 + 一个转换脚本
```

除非假设就是「数据库/流处理是否合适」，否则不要引入数据库或管道系统。

### 前端 / 交互

```text
一个 HTML 页面或模板自带入口 + 一个本地 server
```

只验证交互是否成立；不要先接状态管理、组件库、构建链。

### 并发 / 稳定性

```text
最小并发单元 + 可重复的失败注入 + 日志
```

先证明问题存在，再考虑重试、熔断、队列等机制。

### CLI / 工具想法

```text
argparse + main() + 一个真实用例
```

不要先做插件系统、配置文件、子命令框架。

## 允许升级的情况

只有以下情况可以突破默认预算：

1. **假设本身要求**：例如「验证某框架能否支撑插件化」「验证微服务拆分是否降低耦合」；
2. **简单方案已经失败**，并且失败原因与要验证的目标直接相关；
3. **安全/合规**要求无法回避（例如必须处理真实凭据）；
4. 用户明确要求更完整的实现，并接受时间成本。

升级前写清楚：

```text
简单方案：<已经尝试的最短实现>
失败/不足：<具体现象，不是"感觉不优雅">
需要引入：<框架/服务/分层>
它验证的哪条假设：<对应成功标准>
成本：<新增依赖、启动步骤、维护面>
时间盒与放弃条件：<多久内没有结论就回退>
```

把这段写进 README 或向用户说明，确认后再动手。

## 收尾时的复杂度审计

在 `status success` 之前快速检查：

- [ ] 实验入口是否仍然只有一个（或模板自带的最少入口）？
- [ ] 是否引入了与假设无关的依赖、服务或抽象？
- [ ] 删掉某个模块后，实验结论是否仍然成立？如果成立，为什么要留着？
- [ ] 运行命令是否仍然是一行可复现命令？
- [ ] 如果现在把代码全部丢弃，是否已经留下了足够的结论和数据？

如果最后一项答案是「是」，实验就达到了目的；代码是否优雅不影响结论的价值。

## 一句话

**实验代码的价值在于让你更快知道答案，而不是让你以后少写几行。**
默认写最笨、最短、最容易删除的版本；只有数据证明需要，才升级。
