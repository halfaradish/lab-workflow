# 实验记录模板

README 由 `lab-workflow new` 生成，包含受管区块：

- `## 一句话描述`：由 `meta --description` 维护；
- `## 结论`：由 `meta --conclusion` 维护；
- 顶部元数据表：由 `status` / `meta` 维护。

这些区块的 `<!-- lab:...:start/end -->` 内不要手写，否则下次同步会被覆盖。
`## 假设`、`## 方法`、`## 运行方式`、`## 结果与观察`、`## 下一步` 不受管理，适合写
目标契约、命令、原始数据和推理。

## 一、目标契约（写代码前）

复制到 `## 假设` / `## 方法` / `## 运行方式`：

```markdown
## 假设

在 <条件> 下，<方案/改动> 相比 <基线> 会在 <指标> 上达到 <可观察的差异>。

### 成功标准

- 通过：<可测量条件，例如 p95 ≤ 80ms，或 3/3 次运行稳定>;
- 失败：<明确的反面条件>;
- 判定方式：<怎么测、跑几轮、用什么数据>;
- 环境：<机器、版本、数据量、网络条件>.

### 非目标

- 不做 <生产部署 / UI / 认证 / 持久化 / 多用户 ...>;
- 不验证 <与当前假设无关的性能/兼容性/开发效率>.

## 方法

### 最小实现

- <单文件脚本 / 一个命令 / 一个最小页面>;
- 依赖：<标准库 + 至多 N 个必要依赖>;
- 复用：<共用同一份输入和计时逻辑，避免为每个方案搭一套框架>.

### 时间盒

- <60–120 分钟>；到点无论结果如何都记录。

## 运行方式

```bash
# 实际可复现的命令
{{venv_python}} bench.py --n 100000
```
```

目标契约的作用不是形式化，而是提前锁住范围：没有「非目标」和「最小实现」，实验很
容易滑向搭框架。把成功标准/非目标放进 `## 假设`，把最小实现/时间盒放进 `## 方法`；
不要为它们新增一堆顶层章节，保持模板原有结构。

## 二、过程日志（每次有意义运行后追加）

放在 `## 结果与观察`：

```markdown
### 运行记录

| # | 时间 | 命令/输入 | 结果 | 解释 |
| --- | --- | --- | --- | --- |
| 1 | 10:12 | `{{venv_python}} bench.py --n 10000` | A p95=131ms, B p95=109ms | 差距 17%，样本偏小 |
| 2 | 10:28 | `{{venv_python}} bench.py --n 100000` | A p95=142ms, B p95=118ms | 差距 17%，稳定 |
| 3 | 10:41 | 同上，固定 CPU 频率 | A p95=140ms, B p95=116ms | 差距 17%，排除降频 |

### 意外观察

- <与假设无关但值得记录的现象>;
- <失败/报错/环境问题，以及是否影响结论>.
```

要求：

- 写命令和原始数字，不只写「更快」「更好」；
- 失败的运行也要记，不要只保留成功样本；
- 事后不要修改历史数字；补充解释可以另起一行。

## 三、结果总结（实验结束）

详细推理放在 `## 结果与观察` 末尾或自建 `## 讨论`；`## 结论` 通过 CLI 写入。

```markdown
## 结果与观察

### 结论草稿

- 结论：<一句话>;
- 证据：<关键数字、轮次、对照>;
- 置信度与局限：<样本量、环境、未覆盖的场景>;
- 对假设的判断：支持 / 部分支持 / 证伪 / 不确定;
- 下一步：归档 / 晋升 / 另开实验验证 <新问题>.
```

```bash
"$LAB" meta <ref> \
  --summary "<一句话结果>" \
  --conclusion "<一句话结论，含是否支持假设>" \
  --tags <最终标签>
"$LAB" status <ref> success
```

最后 `"$LAB" show <ref>` 确认状态、摘要、结论和路径。

`SUCCESS` 表示「有结论、值得保留」，不表示假设一定成立。负面结果同样应记录为
success，再按用户决定 archive 或 discard。

## 四、完整示例：延迟对比

```markdown
## 假设

在同一台机器、同一份 10 万条请求数据上，asyncio 方案的 p95 延迟比线程池方案低
至少 20%。

### 成功标准

- 通过：asyncio p95 中位数 ≤ 线程池 p95 中位数的 80%；
- 失败：差距 < 10%，或 5 轮内波动超过 15%；
- 每轮 10 万条请求，本地回环，固定 CPU 频率。

### 非目标

- 不做生产部署、不做错误重试、不做持久化；
- 不比较吞吐上限，只比较 p95。

## 方法

### 最小实现

- 单文件 `bench.py`，标准库 + `aiohttp`；
- 两个函数共用同一份输入和计时器。

### 时间盒

90 分钟。
```

过程日志记录 5 轮数据；结论：

```text
结论：asyncio p95 比线程池低 17%，未达到 20% 的阈值。
证据：5 轮中位数 118ms vs 142ms；详见运行记录。
置信度与局限：单机、回环、固定数据；未测长连接和错误率。
对假设的判断：部分支持，但不足以支撑替换。
下一步：若继续，先测长连接；否则归档。
```

```bash
"$LAB" meta <ref> \
  --summary "asyncio p95 低 17%，未达 20% 阈值" \
  --conclusion "部分支持假设，但不足以替换线程池方案" \
  --tags network,perf,negative-result
"$LAB" status <ref> success
"$LAB" archive <ref>
```

## 五、反例：不要这样记录

```markdown
## 结论

试了一下，感觉 B 更快，应该可以用。
```

问题：没有数据、没有成功标准、没有环境；无法判断是否支持假设，也无法在半年后检索。

更糟的是为了「看起来完整」而引入：

- 为两个 20 行的函数建 `src/`、`domain/`、`services/`、`adapters/`；
- 为一次性数据加 PostgreSQL、ORM 和迁移；
- 为本地脚本加 HTTP API、认证、Docker Compose；
- 为「以后复用」写插件系统和配置层。

这些都不会让实验结论更可信，只会增加解释成本和收尾负担。默认从模板自带的单文件
入口开始；只有假设本身要求，才升级。升级前先写「复杂度升级门」并取得用户同意。
